**What's covered.** The function is one half-open interval, `[due, due + GRACE_DAYS)`, so the tests concentrate where a refactor actually breaks things:

- **The four boundary days** — `due - 1` (out), `due` (in, lower bound inclusive), `due + 4` (in), `due + 5` (out, upper bound exclusive). Each its own test, so a failure names the edge that moved.
- **Window shape derived, not assumed** — tests sweep offsets −30…+30 and assert the in-grace set starts exactly on `due`, is contiguous, and has exactly `GRACE_DAYS` members. A refactor that shifts or fragments the window fails here even if the endpoints happen to line up.
- **Calendar arithmetic** — windows crossing a month end, a year end, a leap day, and a non-leap February. These exist to kill a refactor that reaches for day-number math instead of `timedelta`.
- **Extreme dates** — `date.min` and near `date.max`, for overflow.

**Verification.** A green suite says nothing about whether it would catch a bad refactor, so I mutation-tested it: 12 broken implementations (both bounds flipped, window shifted, window ±1 day, args swapped, due date ignored, naive `today.day - due.day` math, constant changed to 4 and to 6, always-True, always-False). **All 12 were caught**, most by 7+ tests each.

Two things worth knowing:

- **The first mutation run was unreliable and I redid it.** After restoring the original source, 5 tests "failed" against a byte-identical file. Cause: CPython invalidates `.pyc` on source mtime *in whole seconds* plus byte size — the `GRACE_DAYS = 5` → `4` mutant is the same size, and the restore landed in the same second, so stale bytecode kept being served. I re-ran the whole thing with `PYTHONDONTWRITEBYTECODE=1`; the 12/12 above is from that clean run. Flagging it because you'll hit the same trap if you edit `billing.py` and re-run within a second — `find . -name __pycache__ -exec rm -rf {} +` if results ever look impossible.
- **`test_grace_days_is_five` pins the constant deliberately.** If your refactor intentionally changes the grace length, that test *should* fail — delete it then. The rest of the suite reads `GRACE_DAYS` dynamically and will follow the new value.

One observation on the module itself, not acted on: `is_in_grace_period` accepts `datetime` as well as `date` (it's a subclass), and comparison works, but the semantics get murky — a `datetime` of `due` at 14:00 is "in grace", while the exclusive upper bound cuts at midnight. The docstring doesn't say, so I didn't pin behaviour either way. Worth deciding during the refactor.
