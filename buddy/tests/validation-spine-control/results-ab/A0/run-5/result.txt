**Coverage**, grouped by what a refactor could break:
- **Both boundaries** — due date itself is *in* grace (inclusive start), `due + GRACE_DAYS` is *out* (half-open end), plus the two days adjacent to each.
- **The window as a whole** — a parametrized sweep from `due-3` to `due+GRACE_DAYS+3`, a length check, and a contiguity check (exactly one False→True and one True→False transition).
- **Calendar arithmetic** — month, year, and leap-day crossings, which catch a refactor that reaches for day-of-month math instead of `timedelta`.
- **Return type** — `is True` / `is False` throughout, so a rewrite returning a truthy non-bool gets caught.

Most assertions are written against `GRACE_DAYS` rather than the literal `5`, so retuning the constant doesn't break them. One test, `test_grace_days_constant_value`, pins `GRACE_DAYS == 5` so a change to the window length fails loudly in exactly one place.

I verified the suite has teeth rather than assuming it: I ran eight mutants of the implementation (exclusive start, inclusive end, window ±1 day, each bound dropped, truthy non-bool return, naive day-of-month math). All eight were killed, 5–16 failures each, and the original file was restored and diffed clean afterward.

**Two things worth your attention before you refactor:**

1. **`date.max` raises `OverflowError`.** `due + timedelta(days=GRACE_DAYS)` isn't representable when `due` is within 5 days of `date.max`, so the function raises instead of returning a bool. I pinned this with `pytest.raises` and a comment saying so explicitly — it's current behavior, not endorsed behavior. If you refactor to `(today - due).days < GRACE_DAYS` it returns `True` and that test fails; that's an improvement, so update the test rather than preserving the quirk. Probably academic for invoice dates, but it's a genuine behavioral difference between two natural implementations.

2. **The docstring is ambiguous about whether the due date counts.** "The grace period is `GRACE_DAYS` days long" doesn't say whether day one is the due date or the day after. The implementation counts the due date itself, so an invoice due the 10th is out of grace on the 15th, not the 16th. I pinned the current reading, but if the business rule is actually "5 days *after* the due date," the code has an off-by-one today and the refactor is your chance to fix it — in which case `test_first_day_after_grace_is_excluded` and the sweep are the tests to update.
