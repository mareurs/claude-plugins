**Two spec readings I had to fix to write any boundary assertion at all** — both documented in the test module docstring, since a refactor could reasonably revisit either:

1. **The due date itself is in grace.** The docstring names exactly one exclusion — "not yet due" — and on `due` the invoice *is* due. So the window opens at `due`.
2. **`due + GRACE_DAYS` is the first day out**, i.e. in-grace days are `{due … due+4}`. This is the thin spot. The competing convention — "GRACE_DAYS days *after* the due date" — would shift both edges by one and make `due+5` True. `test_last_day_in_grace_period` and `test_first_day_after_grace_period` are deliberately separate tests so that if the refactor adopts that convention, those two are what you change, rather than finding half the suite red and being tempted to delete it.

**One test is implementation-coupled on purpose.** `test_length_follows_the_grace_days_constant` monkeypatches the module global, because a function that hardcoded `5` is invisible to every other test here — it's the single test that caught that mutant. It assumes the constant is read at call time, so a refactor to `is_in_grace_period(due, today, grace_days=GRACE_DAYS)` would break it while staying faithful to the docstring. Rewrite it to pass the argument rather than dropping it.

Two things I pinned but want to flag as **not** spec-backed:

- `test_date_max_due_does_not_overflow` asserts `OverflowError` at `date.max`. That's forced by timedelta arithmetic, not promised by the docstring. If you clamp or return `False` instead, that's a deliberate contract change.
- `test_grace_days_is_five` exists only so that retuning the constant fails once with an explanation, instead of producing a dozen opaque failures from the hardcoded offsets.

I left `datetime`-in-place-of-`date` unasserted — the type contract says `date`, so no behaviour is owed there. It's noted in a comment at the bottom rather than silently omitted.
