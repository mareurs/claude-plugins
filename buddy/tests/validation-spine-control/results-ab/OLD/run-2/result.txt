Done. **19 tests, all passing**, in `tests/test_billing.py` plus a `conftest.py` that puts `src/` on the path. `src/billing.py` is byte-for-byte unchanged.

Since the point is to protect a refactor, passing was not the bar — a suite that can't fail would pass too. So I ran every test against eight one-line mutations of the function body. All eight were caught:

| Mutation | Caught by |
|---|---|
| `due <= today` → `due < today` | due-today, exact-length, bool |
| window one day short | last-day, calendar×4, constant, exact-length |
| close bound `<` → `<=` | first-day-after, calendar×4, exact-length |
| drop the not-yet-due guard | not-yet-due×5, exact-length |
| hardcode `5` for `GRACE_DAYS` | constant test only |
| naive `due.day + N` arithmetic | calendar×4 |
| always `True` | 17 tests |
| return truthy non-bool | bool test |

Three things worth your attention before you refactor:

**I deleted a test I'd written.** `test_does_not_mutate_its_arguments` survived every mutation — `datetime.date` is immutable, so no edit to the body could ever make it fail. It looked like purity coverage while being structurally incapable of reporting a regression. There's a comment in its place explaining the absence.

**One test is intentionally coupled to how `GRACE_DAYS` is bound.** `test_grace_window_honours_the_grace_days_constant` monkeypatches the module attribute, so it only passes while the constant is read at *call* time. If your refactor moves it to a default argument (`grace_days=GRACE_DAYS`) or a config object, this test goes red even though behaviour at the real value is unchanged. That's a binding change, not a regression — retarget the test, don't delete it. It's flagged in the docstring, and it's the sole guard against someone hardcoding `5`.

**Two docstring readings are now pinned as the contract**, and these are the ones a refactor is most likely to drift on:
- `today == due` → **True** ("not yet due is not in grace" implies due-today *is*).
- `today == due + 5` → **False** (a 5-day window opening on `due` covers `due`…`due+4`).

Both come from the docstring rather than from what the code returns. If either reading is actually wrong about your billing rules, the current implementation is wrong too, and `test_grace_period_is_exactly_grace_days_long` is the one place to correct it — it sweeps offsets −10…+20 and asserts the True set is exactly `{0..4}`, so it catches any off-by-one even if the single-point tests get edited.
