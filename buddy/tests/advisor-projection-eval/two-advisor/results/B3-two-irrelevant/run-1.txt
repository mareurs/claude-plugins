## Contract

Given an invoice id, `get_invoice` returns `invoice.render()` if the invoice exists and the caller is an admin or belongs to the invoice's org. It raises `NotFound` if no invoice has that id, and `Forbidden` if the caller is a non-admin from a different org.

## What the existing test pins

**Mutation-survival check on the one test:** it uses an admin whose `org_id` (1) also matches the invoice's `org_id` (1). That makes it blind to the authorization condition. Mutations that stay green:

- Delete the `Forbidden` check entirely.
- Change `!=` to `==` on the role comparison.
- Change `and` to `or`.
- Replace `invoice.org_id != request.user.org_id` with `False`.

It does catch: removing `.render()`, or returning something other than the rendered invoice. That is all.

Two of these deserve a decision, not just a test:

- **`None` on both sides.** If `user.org_id` and `invoice.org_id` are both `None`, then `None != None` is `False` and a non-admin passes the check. Whether that is intended depends on whether `org_id` is nullable in your schema. If it is, that is a possible authorization bypass, and this test pins the answer.
- **Role case sensitivity.** `"Admin"` is treated as non-admin. That is probably correct, but it is a security-relevant edge, so pin it.

## Properties

A metamorphic relation fits here: **for any non-admin user, changing `invoice.org_id` to differ from `user.org_id` must flip the outcome from success to `Forbidden`, and an admin's outcome must not change.** A generator over (role, user_org, invoice_org) that checks the outcome against a one-line oracle (`admin or orgs equal`) covers the matrix. It sits beside the named cases above and does not replace them.

## Open gaps and things I could not verify

- **`db` isolation.** I don't know whether the test's `make_invoice` writes to a real or in-memory DB. If `get_invoice` queries a shared global `db`, test ordering and leftover rows are a risk; each test should tear down its own state.
- **`render()` failure.** If `render()` can raise, nothing tests how that propagates. I can't tell from the snippet whether that is in the contract.
- **Exception identity.** Assert on the exception type (`pytest.raises(NotFound)` / `Forbidden`), not just that something was raised. Otherwise an `AttributeError` from a removed guard can satisfy a loose check.
- **The existing assertion is partly tautological.** `get_invoice(req, 42) == inv.render()` is meaningful only if `render()` is deterministic and has no timestamps or ids that differ per call. Worth confirming.
