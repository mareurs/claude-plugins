Your one test passes. That does not mean `get_invoice` is correct. It pins one path out of four, and it pins that path in the one configuration where the authorization check is never evaluated.

**Contract:** Given an invoice id, `get_invoice` returns `invoice.render()` if the caller is an admin or belongs to the invoice's org. It raises `NotFound` if no invoice has that id, and `Forbidden` if the invoice exists but belongs to another org and the caller is not an admin.

## What the existing test pins

The user is `admin`, so `request.user.role != "admin"` is `False` and short-circuits. `invoice.org_id != request.user.org_id` is never evaluated. The test also sets `org_id=1` on both sides, so even a version that dropped the role check and kept only the org comparison would pass.

**Mutation-survival of the existing test:**
- Delete the whole `Forbidden` line: still green.
- Flip `!=` to `==` on the org comparison: still green.
- Change `NotFound` to return `None`: still green.
- Swap `and` for `or`: still green, because the admin branch short-circuits before the org check matters.

The test catches almost nothing except "returns something other than `render()`".

## Boundaries

- **`invoice_id`:** missing id, `None`, a wrong type (`"42"` vs `42`), a negative number, `0`. Whether the query layer coerces or rejects these is a contract decision the code doesn't state, so I'd ask you before pinning it.
- **`org_id`:** `None` on the invoice with a `None` user org. `None != None` is `False`, so a non-admin with no org could read an org-less invoice. This is the most dangerous edge in the function and needs an explicit test, whichever behavior you decide is correct.
- **`role`:** `None` or missing, an unknown role. Test 6 covers these.
- **Id type mismatch:** `org_id` stored as `int` and the user's as `str` (`1 != "1"` is `True`), which would wrongly forbid a legitimate user.
