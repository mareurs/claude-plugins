## Missing, in priority order

1. **`Forbidden` is never reached.** A non-admin in another org must raise `Forbidden`. This is the security contract, and today nothing guards it.
2. **`NotFound` is never reached.** A missing id must raise `NotFound`.
3. **The admin bypass is not distinguished.** You need an admin whose org differs from the invoice's org (must succeed). Without it, nothing separates "admin bypasses" from "everyone passes."
4. **Non-admin same-org is untested.** This is the ordinary user path, and it needs a positive test.
5. **The lookup is not pinned to the id.** Seed a decoy invoice with a different id, a different org, and a distinct `render()`. Otherwise `.first()` returning any row passes.
6. **Role boundaries.** `"Admin"`, `"superadmin"`, `""`, and `None` must all be treated as non-admin. The check is an exact string compare.
7. **`org_id` boundaries.**
   - **Both `None`:** `None == None` grants access. Is that intended? It is a likely hole for users or invoices without an org.
   - **Type mismatch:** `"1"` vs `1`.
   - **Zero:** `0` is falsy but valid.
8. **`invoice_id` boundaries.** `0`, negative, `None`, and a string `"42"`. Whether these return `NotFound` or something else depends on the ORM's coercion, so verify before asserting.
9. **Failure ordering.** A non-admin asking for a nonexistent id gets `NotFound`. One asking for another org's id gets `Forbidden`. That difference lets a caller probe which ids exist, so decide whether it is intended. Pin whichever you choose with a named test.
10. **`render()` failures and `request.user` of `None`.** Neither has a stated contract. I will not guess one, so tell me what you want.
