*The Testing Snow Leopard pads in, eyes already on the shadows.*

Your tests pass. That does not mean your code is correct. There is one test, and it covers one of four paths.

**Contract:** `get_invoice(request, invoice_id)` returns `invoice.render()` if the invoice exists and the user is an admin or belongs to the invoice's org. It raises `NotFound` if no invoice has that id. It raises `Forbidden` if the user is a non-admin from a different org.

## What the existing test pins

`test_get_invoice_returns_rendered_invoice` uses an admin whose org also matches (`org_id=1` on both sides). It exercises the happy path through the first operand of the `or`, and it is weaker than it looks:

- **The admin and org-match conditions are conflated.** The user is both admin and same-org, so the test cannot tell which condition let the request through. Deleting the `role != "admin"` clause entirely, so the check becomes `invoice.org_id != request.user.org_id`, leaves it green. So does flipping `!=` to `==` on the role comparison.
- **The authorization branch is never entered with a denial.** Change `Forbidden` to `return None` and nothing fails.
- **`NotFound` is unreachable.** No test passes a missing id.

Tests 3 and 4 are the most important. They split the existing test's conflated condition into its two independent halves.

## Boundaries not yet listed

- **`invoice_id` types:** `None`, a string `"42"`, 0, and negative values. What the DB layer does with them depends on the ORM and column type. I haven't seen either, so I can't say what the contract promises here. That decision needs to be made before a test is written.
- **`org_id` of `None`:** a user with `org_id=None` and an invoice with `org_id=None` compare equal, so a non-admin passes. Whether that's intended is a contract question. If an invoice can have a null org, this is an authorization bypass, so decide and pin it.
- **Role values:** `"Admin"`, `"admin "`, `""`, `None`. The comparison is exact-string, so anything but `"admin"` takes the org path. One parameterized row each pins that this is intended.
- **Type mismatch on org:** `org_id` of `1` vs `"1"`. Python's `!=` treats them as different, so a non-admin would get `Forbidden` on their own invoice. This is a plausible real-world bug if one side comes from a JWT claim or a query string.
- **Admin on missing invoice:** an admin asking for a nonexistent id should still get `NotFound`. This is cheap to add to test 2 as a parameter.

## Properties worth adding

- **Metamorphic:** for any non-admin user and invoice, the result is a render if and only if `user.org_id == invoice.org_id`. Make `org_id` the generated variable and the role fixed.
- **Admin invariance:** for any admin and any existing invoice, the result equals `invoice.render()` regardless of `org_id`.

These sit beside the named cases above. They don't replace them.

## Test-quality note on the existing test

`assert get_invoice(req, 42) == inv.render()` compares the output to `inv.render()` called on the same object. If `render()` is deterministic this is fine. If it includes a timestamp or a random token, the test is flaky. I haven't seen `render()`, so I'd check that. The test also never shows that `make_invoice` persists into the DB that `get_invoice` queries. If `make_invoice` only builds an object, the test could be passing against a different fixture setup than I assume. Show me `make_invoice` and the `db` fixture, and I'll confirm.

## Suggested format for the first gap

**Contract:** a non-admin user cannot read an invoice belonging to another org.
**Boundaries covered:** role (non-admin), org mismatch.
**Arrange / Act / Assert:** persist invoice (org 1), build request (member, org 2), call `get_invoice`, assert `Forbidden` raised.
**Properties:** none for this single case. The metamorphic org property above covers the space.
**Mutation-survival:** removing the `Forbidden` branch, or flipping `!=` to `==` on the org comparison.
**Isolation:** real or in-memory DB, torn down per test.
**Pyramid level:** unit.
**Confidence:** high.
**Open gaps:** null orgs, type mismatch on org id, odd role strings.
