Your one test passes, but it pins almost nothing. It covers one of three outcomes, and it sets the user's org and the invoice's org to the same value (`1`), so the authorization line never has to make a decision.

## Contract

Given an invoice id and a user:
- unknown id → `NotFound`
- non-admin whose `org_id` differs from the invoice's → `Forbidden`
- admin (any org) or same-org user → `invoice.render()` of the invoice with that id

## What the existing test would miss

| Mutation in `get_invoice` | Existing test |
|---|---|
| Delete the `Forbidden` line entirely | stays green |
| `!= "admin"` → `== "admin"` | stays green (orgs match, so the admin check never matters) |
| `and` → `or` | stays green (admin and same org) |
| Delete the `NotFound` check | stays green (the invoice exists) |
| Filter on the wrong column, if the table holds only this row | stays green |

The test only fails if `render()` is dropped or changed. All access control is unpinned.

## Missing tests

Ordered by the risk they cover:

1. **Non-admin, other org → `Forbidden`.** Pins the core tenant isolation.
2. **Admin, other org → returns the invoice.** This is the only test that discriminates the admin bypass. Without it, the existing test would pass even if the bypass were deleted.
3. **Non-admin, same org → returns the invoice.** Guards against an over-tight check (`or` instead of `and`). Right now the happy path is only exercised as an admin.
4. **Unknown id → `NotFound`.** Assert the specific type, not just "an exception".
5. **Right row selected.** Seed at least two invoices with distinct ids, orgs and rendered content, then assert you got the one you asked for. With one row, a broken filter is invisible. Also make sure `render()` differs between the invoices, or the equality assertion is vacuous.
6. **Role boundaries.** Non-`"admin"` roles (`"Admin"`, `"administrator"`, `""`, `"staff"`) get no bypass. This pins the exact string comparison.
7. **Null org boundary.** If `org_id` is nullable, a user with `org_id=None` and an invoice with `org_id=None` satisfy `==` and pass the check. I haven't seen the model, so I can't say whether that state is reachable. Check it, then pin whichever behavior you want.
8. **Check ordering.** A non-admin asking for a nonexistent id gets `NotFound`, but for another org's id gets `Forbidden`. That lets them probe which ids exist. Whether that matters is your call, since it's a contract decision. Either way, write a test that pins the order so a refactor can't change it silently.
9. **Bad id inputs** (`0`, negative, `None`, a string). Expect `NotFound` or a type error, whichever you intend. The ORM parameterizes the query, so I'm not flagging injection here.

I'd also ask where an unauthenticated request (`request.user is None`) is handled. Here it would raise `AttributeError`. If middleware guarantees a user, say so in a comment.
