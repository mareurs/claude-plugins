# The harness of this repository

The harness is everything under `.codescout/` that makes a session in this repository work: the memories, the verbs, the system prompt and the key space.
`codescout box` is the entry point: a short view that routes to every box.
`codescout box add` files in `runtime`, the root ledger, anything that no other box takes.
Each box in the view says what it takes.

`codescout box <key>` opens one box, a collection with its readme, hot view and verbs. This file is the index of the root box: it says what lives where, and it lists no entries and no verbs (`codescout box` lists the verbs it finds).

## What is committed, what is regenerable

Committed:

- `memories/`: the codescout memories of this repository.
- `box/scripts/`: the verbs, `box/scripts/<key>/<verb>.py` for the box `<key>`, `box/scripts/<verb>.py` for the root. `box/templates/`: the templates of this repository.
- `py/requirements.txt`: the manifest of the Python environment. It is committed when it exists; this repository has none today.
- The configuration files (`key-space.toml`, `librarian.toml`, `repo.toml`, `requirements.toml`) are committed when they exist. This repository commits none: `repo.toml`, `project.toml` and `workspace.toml` stay local.
- `system-prompt.md`: the project text added to the server prompt.
- `audit/`, `measurements/`: recorded evidence, when a repository has any. This one has none.

Regenerable, and not committed: the databases (`*.db`), the logs and the locks, which `.gitignore` names, and `box/state/<key>/`, the state of the verbs, which holds its own `.gitignore`. The Python environment is outside the checkout, in `<state dir>/codescout/venvs/<project key>/`; `codescout py status` shows it.

This repository's `.gitignore` ignores `.codescout/*` and whitelists `memories/`, `box/`, `system-prompt.md` and `harness.md`; it ignores `box/state/` again. A new committed path under `.codescout/` needs a whitelist line there.

## The core verbs

Every box has fifteen verbs that the binary answers itself: `add`, `check`, `close`, `decisions`, `edit`, `end`, `find`, `help`, `list`, `now`, `promote`, `reaffirm`, `show`, `supersede` and `timeline`. The core card (`codescout box help`) lists them, `codescout box help <verb>` gives the flags of each, and `codescout box <key>` prints the box: its declarations and own verbs, its hot view and its rules. All but `check` run no script and no Python; `check` reports its findings and then runs the box's own `check.py`, if it has one. `list`, `show` and `find` (`find --meaning` ranks by meaning) read a box; `decisions` (the decisions in force) and `timeline` (their history) read the decisions of a box, and with no key, of every box. `add` files one entry through the `doc` door, prints its key, and commits it when the readme says `commit: new-entries`; `now`, `edit` and `close` change one entry, commit nothing and print the one `git commit` line to run. `supersede` files a decision that replaces one or more old decisions and closes each as `superseded`; `reaffirm` records that a decision still holds and re-hashes its anchors (`add --anchor` sets them); both commit nothing and print the `git commit` line to run. `promote <entry> --to <box>` files the entry in another box through that box's `add`, closes the source as `promoted` with a `**Promoted to:**` line and links the two ends; `--to-file <path>` records a file of the repository instead. A source box must declare `promoted: terminal`. It commits nothing and prints one `git commit` line that names both files. `end` moves a finished stream (every entry terminal, no entry file unread) to `streams/archive/<key>`, refuses a ledger and a stream with an open entry, commits nothing and prints the `git add` and `git commit` lines for both folders; the catalog then holds old rows with the history, so each moved file needs a `doc` graft after a reindex (the answer says how). The root view lists a stream under `can end` and under `stalled`. A box that holds decisions declares `decision` among its kinds and `superseded: terminal` among its statuses. A box write is refused in a linked git worktree. The fifteen names are reserved verb names in every box, and no box is named so: they are reserved keys, as `help`, `new` and `scratch` are. `codescout box help` prints the core card, and `codescout box <key> <verb> --help` prints the docstring of a script verb. The first `codescout box` call of a Claude Code session prints the card once; later calls print one `core:` line that names `codescout box help`. A trailing `--json` is honoured by the core verbs. Each core verb run, each script verb run and each open writes one `call:box` row in `usage.db` when the project has one, and each script run of `codescout py` by hand writes one `call:py` row (`py status`, `sync`, `add` and `clean` write none). A row of a failed run holds `exit code N: <the last lines of its output>`; `codescout box frictions recent` lists them.

Without a key, a core verb other than `help`, `decisions` and `timeline` acts on `runtime`: `codescout box add|list|show|now|close|edit` read and write the ledger, `codescout box find` searches every live box, and `codescout box check` reports the ledger's findings and the box candidates. `codescout box runtime <verb>` is the same ledger as a normal box view. Flags of `box` itself (`--project`, `--json`, `--help`) go before the verb.

A script with a core name never answers to that name, with one exception: `check.py` runs after the core `check` as the box's own extra check step, and the open view lists it under `own verbs:` as `check: … (runs after the core check)`. A script named after any other core verb is never run; the open view lists it as `shadowed scripts, never run:`, and `codescout box <key> check` reports it.

## Making a box

`codescout box new` lists the templates. `codescout box new <template> <key> --title "<title>"` makes the box from one and prints the commit line. `<template>` is a name, or the path of a template folder (it has a `/` or starts with `.`, and is read from the current folder); a name no template has is read as the folder `./<name>` when it holds `readme.md`, and the answer says so.
A template is a folder: `readme.md`, optional verbs `<verb>.py`, the test of each `tests/test_<verb>.py`, and `version` in the readme frontmatter (1 when absent). It is built in, or `.codescout/box/templates/<name>/` of the repository (a folder of the same name replaces a built-in one), or any folder given by path. A folder given by path may not take the name of another template; rename it. A `<name>.md` file in `.codescout/box/templates/` is listed as broken: a template is a folder, and a good folder of the same name stays the template.
`box new` checks everything, then copies the verbs and tests into `.codescout/box/scripts/<key>/`, then writes the readme through the `doc` door with `template` and `template_version`, and removes the copies when the door refuses. It refuses first when the box folder holds files, when a file it would copy exists, or when a folder it copies through is a link (replace the link with the folder). The commit line names every file written.
A test that travels in a bundle finds its verb at `Path(__file__).resolve().parent.parent / "<verb>.py"` and its key at `Path(__file__).resolve().parent.parent.name`, loads the verb by path and starts no binary, so the same bytes pass in the bundle and in every box it makes.
A bundle that sits inside the repository outside `.codescout/box/templates` has its `readme.md` indexed as a document under its folder name, so a box of the same key is refused after the copy (the copy is undone); keep bundles under `.codescout/box/templates`, or name the box differently.
A singleton template of a repository needs `.codescout/box/templates` under `exclude` in `key-space.toml`.
A box owns its readme and its verbs from then on: a change to the template changes no box that exists. To move a box to a newer template, the template author ships a migration script and runs it with `codescout py <script>`; it checks `template_version`, rewrites the readme through the door and the verbs as files, and sets the new version.

## Add a verb

1. Write `.codescout/box/scripts/<key>/<verb>.py`. The verb's name must not be a core name (the fifteen of the card); `check.py` is the one core-named script that runs, after the core `check`. The first line of its module docstring is the description that `codescout box <key>` prints.
2. Import `codescout`, the helper module. A verb reads through `codescout.doc.find_iter` and the like, and writes only through the door `codescout.doc.*` (for example `codescout.doc.create`). It opens no file for writing. The codescout repository checks this with a test; this repository has no such test. A verb is a rule of its box. The store behind the door can change and no verb changes. A verb that takes a JSON object reads it with `codescout.read_input()`, which gives `--text <field> <source>` and `--encoded` to every verb that calls it. A verb that files or changes an entry calls `codescout.box.add`, `now`, `edit` or `close`, which run the core, so it adds its own step and does not copy the core. A script verb parses its own arguments.
3. Add its test as `.codescout/box/scripts/<key>/tests/test_<verb>.py` (a root verb: `.codescout/box/scripts/tests/test_<verb>.py`). The test loads its verb at `Path(__file__).resolve().parent.parent / "<verb>.py"` with a fake `codescout` module and reads its key from `Path(__file__).resolve().parent.parent.name`. The tests of the `frictions` verbs are byte copies of the codescout repository's; `tests/test-frictions-box.sh` runs them, and `tests/run-all.sh` runs every `tests/test-*.sh`.
4. Run it with `codescout box <key> <verb> [args...]`. The arguments reach the verb as they are. A root verb (`box/scripts/<verb>.py`, for work that belongs to no one box, such as `repoint`) runs as `codescout box <verb> [args...]` when no box has that key; a box of the same name wins, and a core name never runs a script. It gets no box variable, no state folder and no commit step, and its `call:box` row has a `null` key. `codescout py .codescout/box/scripts/<verb>.py` runs it too. Its test is `.codescout/box/scripts/tests/test_<verb>.py`.
5. Maintain it. A verb is code that this repository owns, for every box and every template. When the readme of a box changes its fields, statuses or entry kinds, run the verb tests of that box. When a verb has no use left, delete it with its test. A temporary verb (a migration, for example) says so in its docstring and names the event that ends it. No test in this repository requires a test file per verb, and none checks that a verb is still needed.

A root script `.codescout/box/scripts/<verb>.py` runs as `codescout box <verb>` as a root verb (step 4: no ledger needed, nothing is committed), unless a live box has that key. `codescout box runtime <verb>` runs the same file as a verb of the root ledger `runtime`, which commits the entries it creates; use this form for `measure`. There is no `.codescout/box/scripts/runtime/` folder: `runtime` is the root ledger, and `codescout box check` reports such a folder.

## Commit, check

- A collection readme with `commit: new-entries` makes `codescout box <key> <verb>` commit the entries a verb created. `git config codescout.boxCommit false` vetoes it in a checkout. The command exits 1 when the commit step failed (a hook refused, or the commit could not be identified); otherwise the verb's own code passes through.
- A collection readme with `commit: batched` records each write of `add`, `now`, `edit`, `close`, `supersede` and `reaffirm` instead of committing it, and the answer ends with `pending: committed at the end of the turn (codescout box flush)`. `codescout box flush [--session <id>] [--json]` commits what the session recorded, in one commit, by the recorded blob ids; run it at the end of your turn (a `Stop` hook of the companion plugin does this where it is installed) and, in a linked worktree, before you merge that branch (a pending entry is not in the branch until the flush), and every later box call sweeps the records of sessions that are gone (not live, and quiet for an hour). Exit 0 means the flush ran (stuck paths are printed, not errors), 1 the commit step failed or a commit stands and needs a hand (the `stands:` line says what), 2 `NOT DONE`; a busy write lock is exit 1 and keeps every record for the next flush. The root view shows `pending: <n> records of session <id>` for waiting records (with a `flush failed: <reason>` line under it when the last flush of that session did not commit or left a commit that needs a hand; the next clean flush clears it) and `stuck: <path>: <reason>` for a path a flush leaves alone: the working file changed after its last record, a write is missing from the records, HEAD holds another version, a publish hold, or the file was deleted. A stuck path keeps its records until you settle it: commit the path by hand as the reason says (`git add -- <path> && git commit -m "..." -- <path>`, or for a deletion `git rm`), except for a publish hold (the hold of a session keeps its chain; it commits after `scripts/hold-publish.sh release`, and no other session may commit it) and a path that cannot be read (replace or remove it); after the hand commit the next flush drops its records because the working tree then matches HEAD. For a deleted file the reason also gives `git cat-file -p <blob> > <path>` to restore it. Do not commit the files of a batched box by hand otherwise: the flush commits them. An entry that reappears after a peer's `git stash` is committed by hand: the stash made it look done, so its records are gone. A torn line has an exit: commit the entry by hand if it exists, then delete the session file `.codescout/box/state/batched/<sid>.jsonl`. In JSON, the `torn` field of the root view (`codescout box --json`) is a list of `{"file": ..., "line": ...}` objects, while `codescout box flush --json` gives `torn` as a list of `[file, line]` pairs inside its `flush` and `sweep` objects.
- `codescout box <key> check` reports the findings of the collection, then runs `box/scripts/<key>/check.py` if the box has one. Exit 0 means nothing found, 1 findings, 2 not shown or not done; a non-zero code of `check.py` passes through, so a `check.py` that exits 1 or 2 looks like findings or a refusal.

## Platforms

`codescout box` is supported on Unix. It is not supported on Windows for now. The commit step runs `git` as a process and quotes each path as one word of a POSIX shell command line (`quote_path` in the codescout source, `src/cli/boxes/commit.rs`). In the codescout source, the tests of that step that need a symbolic link, a unix file mode or raw file-name bytes are `#[cfg(unix)]`, so they do not run on Windows. No run of `codescout py`, `codescout call doc` or `codescout box` on Windows has been made. Revisit this line when that run is made.

## Safety

A verb runs with the user's full rights. Whoever clones a repository and runs `codescout box <key> <verb>` runs that repository's code, and the permission prompt of the harness and code review are the only gates. A permission rule that allows every `codescout box` call allows every script in the repository.
