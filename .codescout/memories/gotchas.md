# Gotchas

## Cross-Project

- **3 Claude Code instances, not 2.** `~/.claude/`, `~/.claude-sdd/`, `~/.claude-kat/` — all 3 `installed_plugins.json` must be updated on any version bump. (Buddy memory no longer mirrors per-profile: since the shared-home refactor it lives in a single `${BUDDY_HOME:-~/.buddy}` reachable by every instance — see `buddy/scripts/buddy_paths.py`. There is **no** `data/instances.json`; the old per-profile mirror design was abandoned. `buddy/scripts/migrate_global.py` is the one-time merge and already covers all 3 profiles.)
- **installPath profile drift.** `installPath` in installed_plugins.json must start with the owning profile root. Cross-profile paths cause hooks to load from the wrong cache dir.
- **New component types invisible after install.** Adding `commands/` or `skills/` to a plugin requires updating `installPath` in installed_plugins.json to the new cache snapshot — Claude Code freezes the path at install time.
- **Local "directory" marketplace still snapshot-copies per version — editing source files does NOT resync without a version bump.** `sdd-misc-plugins`'s marketplace source is `{"source":"directory","path":"/home/marius/work/claude/claude-plugins"}` (i.e. this repo itself), yet each plugin (e.g. `codescout-companion`) is still installed into a versioned cache snapshot (`~/.claude-<profile>/plugins/cache/sdd-misc-plugins/codescout-companion/<version>/`) keyed off `.claude-plugin/plugin.json`'s `version` field. Editing hook scripts / hooks.json in the source repo has **zero effect** on the running session until the plugin's `version` is bumped — `/reload-plugins` and even `/plugin update <name>` silently no-op against an unchanged version string (confirmed empirically 2026-07-06: two rounds of `/reload-plugins` + one `/plugin update codescout-companion` all left the cache pinned to the old version with the new hook script entirely absent from disk). Only bumping `version` in `plugin.json` + `/plugin update` + `/reload-plugins` actually re-copied the new files into a fresh `<new-version>/` cache dir. **Any plan/task that adds or edits a hook in this plugin must include a version bump as an explicit step — it is not optional polish, it's load-bearing for the change to ever take effect.** See `development-commands` memory's "Version Bump" section for the full checklist.

## PreToolUse Dispatch — MCP Tool Selectivity (OPEN QUESTION, found 2026-07-06)

While verifying three new `codescout-companion` PreToolUse hooks live (constitution-guard.sh/-brief.sh/-epoch-bump.sh, matcher pattern `mcp__codescout__(edit_code|edit_file|create_file)` and similar), extensive empirical testing found:

- `mcp__codescout__run_command` **reliably triggers** PreToolUse dispatch — confirmed unprompted, mid-session, via `il3-warn-hook.sh` (matcher `mcp__.*__run_command`) visibly firing. **⚠ That diagnostic is gone as of companion 1.16.9** (`a989d73`): the warn hook was deleted and the `mcp__.*__run_command` matcher now carries no hook at all, so this observation can no longer be reproduced by watching `run_command`. It stands as a 2026-07-06 measurement, not a repeatable check. To re-test the positive case now, use `il4-deny-hook.mjs` on `mcp__.*__read_file` — an MCP-matched hook that still fires and still blocks.
- `mcp__codescout__create_file` **never triggered any PreToolUse hook**, including the **pre-existing, unmodified** `worktree-write-guard.sh` (matcher `mcp__codescout__(edit_code|edit_file|edit_markdown|create_file)`, predates this session entirely) — confirmed via direct debug-log instrumentation added straight into the live cached script (bypassing the version-bump cache-sync entirely for this test): zero invocations logged across 6 real `create_file` tool calls, even after the plugin cache was correctly synced to the new version and after a claimed full process restart.
- Ruled out: matcher syntax (tested both the grouped-alternation form and a bare exact-tool-name form — neither fired), hook ordering / first-match-wins (neither the first- nor second-registered matcher block for the same tool fired), and the hook script's own logic (proven correct via `echo '<realistic tool-call JSON>' | bash hooks/constitution-guard.sh` against the real `codescout` binary and a real catalog — produces the exact expected `deny` JSON).
- **Not yet confirmed:** whether this is (a) a genuine platform behavior where PreToolUse dispatch for MCP tools is selective by tool/annotation (`run_command` fires, `create_file`/`edit_code`/`edit_file` don't), or (b) the "cold restart" never actually re-spawned a fresh process for the live session under test, despite the user's confirmation. `/hooks` (Claude Code's own registered-hooks UI) was suggested as the next diagnostic but not yet run.
- **Practical implication if (a) is confirmed:** `worktree-write-guard.sh` and the new constitution-guard.sh (both matched on `edit_code|edit_file|edit_markdown|create_file`) may be silently inert for MCP-originated calls in this environment, while `il4-deny-hook.mjs` (matched on `read_file`) works as intended — `il3-warn-hook` was the other half of this comparison and no longer exists, so `read_file` is the only surviving MCP-matched positive control. (Both were `.mjs`, not `.sh`, from the 1.14.0 port onward; the `.sh` names throughout this section are how they were spelled when the note was written.) This would mean the whole `edit_code|edit_file|edit_markdown|create_file` PreToolUse matcher family needs re-validation, not just the constitution hooks.
- **Resume:** run `/hooks` in a live session to confirm/deny registration; if registered but still not dispatching, this needs to be reported/investigated as a Claude Code platform issue rather than a plugin bug.

## codescout-companion Specific

- **`block_reads` must be string `"false"`, not boolean.** jq `// empty` treats boolean `false` as absent, so the boolean form is silently ignored and reads stay blocked. Set `"block_reads": "false"` (quoted string) in `.claude/codescout-companion.json`.
- **`marketplace.json` must have NO version fields.** Claude Code reads version from `plugin.json` at install time; duplicating in marketplace causes silent drift.
- **Always exit 0 in codescout-companion hooks.** Exit 2 ignores stdout — `permissionDecisionReason` never reaches Claude. Use `permissionDecision: "deny"` in JSON output instead.

## buddy Specific

- **Judge config in `judge.env`, not `settings.json`.** Hooks source `judge.env` directly; any value in settings.json would be overridden by the sourced env file.
- **buddy allows exit 2** for hard judge block (`BUDDY_JUDGE_BLOCK=true`) — this is intentional and differs from codescout-companion's exit-0-only rule.
- **`set -e` + command-substitution in buddy hooks.** buddy hook scripts run under `set -e`. A bare `VAR=$(python3 -c "…" 2>/dev/null)` aborts the whole hook if the python exits non-zero (the `2>/dev/null` hides the trace but not the exit code). Append `|| true` to every such advisory assignment so a nudge-path hiccup can't take down the critical session-reset/persona-reload block. (Fixed in `session-start.sh` 2026-06-14; the migrate + final state-handler calls were already guarded.)
- **Subagent detection in SessionStart.** buddy distinguishes subagents from real sessions via `source=="startup"` + session_id diff + 600s window. Real sessions get full signal reset; subagents get only their own narrative/verdicts cleared.
- **Repo name drift.** Old docs/configs reference `sdd-misc-plugins` (previous GitHub repo name); current name is `claude-plugins` (`mareurs/claude-plugins`).
- **`loaded_skills.json` is eventually-consistent (scan-lag).** The statusline skill ledger (`.buddy/<sid>/loaded_skills.json`) is written ONLY by buddy hooks calling `scan_transcript` (`buddy/scripts/skill_ledger.py`), which reads transcript bytes past the saved `transcript_offset`. A `Skill` `tool_use` line written *after* the last scan won't register until the next hook fires — so a mid-turn read of the ledger can show stale/empty `"skills": {}` even though the load is already in the transcript. (Verified 2026-06-16: Skill line began at byte 460387, ledger `transcript_offset` was 457319 → ledger looked empty; NOT a detection bug.) Before concluding a skill "didn't register," compare the Skill-line byte offset (`grep -b '"name":"Skill"'`) against the ledger's `transcript_offset`, or force a `scan_transcript` pass — don't trust the snapshot. Same applies to the `cs:`/`skills:` statusline lines, which read from this ledger.

## Tool Routing (codescout MCP)

- **Markdown ops are the #1 Iron-Law slip in this repo.** A month of `.codescout/usage.db` (5961 calls) shows 135 server rejections for wrong-tool routing; 68 are markdown — `read_file`→`read_markdown` (39, IL4) and `edit_file`→`edit_markdown` (29, IL5). This repo is docs-dense (`docs/trackers/`, `docs/superpowers/specs/`, `*/SKILL.md`, `CLAUDE.md`) — reach for `read_markdown`/`edit_markdown` on any `.md` *first*, before the server bounces you. Source slips trail behind: `read_file` on source→`symbols(include_body=true)` (45, IL1), `edit_file` with `def`→`edit_code` (22, IL2). Full evidence: `docs/trackers/codescout-usage-audit-session-log.md` (U-1..U-4).
