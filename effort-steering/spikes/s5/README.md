# S5 — does an effort-steering sentence hurt coding quality?

Throwaway spike code (ES-10: no `plugin.json`, no marketplace entry, no README row). S5 runs a coding agent in Docker on real fix-commit tasks in three arms and decides whether the S4 steering sentence ("Answer directly without deliberating.") costs quality. The design is `docs/superpowers/specs/2026-10-07-effort-steering-quality-test-design.md`, the plan `docs/superpowers/plans/2026-10-07-effort-steering-quality-test.md`.

| Arm | Setting | Runs per task (measured) | Runs per task (calibration) |
|---|---|---|---|
| A | `xhigh`, no steer | 3 | 2 |
| B | `xhigh` plus the steer | 3 | 0 |
| C | `low`, no steer | 2 | 1 |

This file has four parts: how the CLI behaves, the **runbook** (the operator gates, with the exact commands), the **instrument rules** (what the code enforces and what a person must do by hand) and, last, what is **not** verified. Every rule names the file or ruling it comes from (`R<n>` is a ruling in the SDD ledger), so a reader can check it.

All commands run from the repository root of the worktree. Below, `S5` stands for

```
S5="node effort-steering/spikes/s5/s5.mjs"
```

## 1. The CLI

`s5.mjs` only wires the existing modules together: argument parsing, the token file, exit codes and printing are its own; everything else is `mine.mjs`, `build-task.mjs`, `gate-task.mjs`, `proxy.mjs`, `prereg.mjs`, `run.mjs`, `analyze.mjs`, `grade.mjs` and `images/build.sh`. `$S5 --help` lists the subcommands; each usage error names the synopsis of the subcommand.

| Subcommand | What it does | Prints on stdout |
|---|---|---|
| `mine --repo <name>=<dir> ... [--since <date>] [--out <file>]` | `mineCommits` over each repo; writes the candidates (default `effort-steering/spikes/s5/tasks/candidates.json`, window default `2026-09-28`) | `{ out, count, perRepo }` |
| `build <taskDir>` | `buildTask` into `<work-root>/tasks/<id>/` | the manifest without `def`: `id, repo, fix, parent, baseCommit, treeHash, hiddenHash, promptHash, taskMdHash` |
| `warm <taskId> [--prereg <file> [--mode <m>]] [--cpus <n>] [--memory-gb <n>]` | `warmTask` (cargo tasks only; others answer `skipped: 'not cargo'`), under the given limits (R150, below) | the result |
| `gate <taskId> [--prereg <file> [--mode <m>]] [--cpus <n>] [--memory-gb <n>]` | `gateTask`, under the given limits; writes `<work-root>/tasks/<id>/gate.json` | `{ taskId, ok, reasons, gatedAt, leftover }` |
| `images` | runs `images/build.sh`, forwards its progress to stderr | `images/digests.json` |
| `proxy up (--log-all \| --prereg <file> [--mode <m>])`, `proxy down`, `proxy log` | `proxyUp`, `proxyDown`, `proxyLog` | the result; the log text |
| `run --mode <measure\|pilot\|calibrate\|smoke> --prereg <file> [--tasks <ids>] [--rows <file>] [--concurrency <n>] [--stop-at-cost <usd>] [--retry-exhausted] [--keep-run-dirs] [--open-network] [--token-file <file>]` | `runBatch` | the Summary, once, at the end (nothing is printed while the batch runs: watch the rows file) |
| `grade <runId> [--prereg <file> [--mode <m>]] [--cpus <n>] [--memory-gb <n>]` | re-grades a kept run directory, under the given limits | the grade |
| `select --rows <file>` | `selectCalibrated` | `{ kept, dropped }` with a reason per dropped task |
| `analyze --prereg <file> --rows <file>` | `analyzeS5` | the Report |
| `simulate [...]` | the planted-truth simulation | `{ params, scenarios }` |

**Exit codes** (same for every subcommand). `0`: it did what it was asked; for `run` that includes a batch that **stopped by a rule** (cost, signal, `infra_streak`, `hidden_changed`, `plan_limit`): read `stopped` in the Summary, and for a smoke run `smoke.ok`. `1`: a module threw or refused, a file or manifest could not be read, the token file was refused, or the answer is no (`gate` not ok; `warm` whose build failed). `64`: a malformed command line (usage on stderr, nothing on stdout), as `effort-policy` does. Errors start with `s5: <subcommand>: <message>` on stderr (a module's own message can span several lines).

**Limits of `warm`, `gate` and `grade`** (R150; `s5.mjs`). The measured runs and their grades run with the registered `--cpus` and `--memory`; the gate's flaky filter (the fix tree three times), its build-timeout check and the warm build are measurements too, and on an unconstrained host they are another instrument (a build that fits `timeoutsSec.build` there can exceed it under `--cpus`, and a test that is timing-sensitive passes the gate and is flaky in the grades). So the three subcommands take `--prereg <file>` (the limits `cpus` and `memoryGb` of the registration; with `--mode <m>` of a config, loaded as `run` loads it, default `measure`) and/or `--cpus <n>` and `--memory-gb <n>`. An explicit flag wins over the file; `--mode` without `--prereg`, a limit that is not a number above 0 and a file without positive `limits.cpus` and `limits.memoryGb` are refused before `gateTask`, `warmTask` or `gradeTree` is called (exit 64, or 1 for the file, which the loader has already read). With none of them nothing is passed and the container is unconstrained, as before. `gate.json` does not record the limits it was made under: write them down.

**Work root.** Every subcommand that touches built tasks takes `--work-root <dir>`, default `~/work/claude/s5-work` (`DEFAULT_WORK_ROOT` in `proxy.mjs`). Never `/tmp`: it is a 24 GB tmpfs. The work root holds `tasks/<id>/{tree,hidden,prompt.txt,manifest.json,gate.json,target}`, `runs/<runId>-a<N>/{config,state[,work,target]}`, `cargo-home/`, `proxy/`, `hook/`, `grades/`, `gate/`, `warm/`, `rows-<mode>.jsonl` and, while a batch runs, `batch.lock`.

**Which loader.** `run --mode measure` loads the file with `loadS5Prereg` (the committed registration: bytes equal to the HEAD blob, at least 8 tasks, A >= 2, B >= 2, C >= 1 runs). `smoke`, `pilot` and `calibrate` load it with `loadS5Config(file, { mode })`: the same shape, no commit needed, an arm may have `runs: 0`, one task is enough. A config is never accepted as a registration, and neither loader accepts a `registered` key in the file (R2, R59). `proxy up --prereg` chooses the loader the same way (`--mode`, default `measure`); `analyze` always uses `loadS5Prereg`.

**The token** (`run` only; no other subcommand reads it; R108). The OAuth token from `claude setup-token` is read from `~/.config/s5/token` (override `--token-file`), unless `CLAUDE_CODE_OAUTH_TOKEN` is already set and not empty in the environment (then the file is not touched, but the **same value check** applies to that value, R145, and the message names the variable; `runBatch` gets the validated value and your own variable is put back untouched afterwards). The CLI **refuses** a file that is a symlink, that is not a regular file (a FIFO is refused, the open does not wait for a writer), that has any group or other permission bit (`mode & 0o077`), that is missing, or that is empty; the message names the path (and the mode) and never a value, and the mode is checked before the bytes are read. All trailing whitespace of the value is dropped (newlines, CRLF, spaces), and a value that still holds whitespace or a control character inside is refused too (R143: a token has none, and a newline in it would fail authentication in every run, looking like infrastructure); the message names the path, never the value. The value is put into the process environment for the duration of `runBatch` only and taken out again; it is never in an argument list, an option, a file or the printed Summary, and everything `run` prints is passed through a redaction of the value as a last line of defence. Create the file without leaving the value in your shell history: see gate 0.

## 2. Runbook

Eight gates; gates 3, 5, 6 and 7 need the operator's approval before anything runs. The counts are from the plan and the spec; the **costs are derived, not measured**: the spec quotes published figures of about $2 to $5 per run at `xhigh` and about $0.8 at `low` ("not our measurement"), and on the subscription the cost is plan usage, not a bill. The multiplication below is mine. The pilot replaces it with the client estimate (`costUsd` in each row, the stdout `total_cost_usd`) and the plan usage the operator reads off the usage page before and after.

| Gate | What | Approval | Runs | Derived cost |
|---|---|---|---|---|
| 0 | token | operator does it | 0 | none |
| 1 | mine | no | 0 | none |
| 2 | pilot tasks | no | 0 (Docker builds and test runs, no model) | none |
| 3 | pilot (smoke first) | **yes** | about 16 (13 + 3 smoke) | $27.2 to $63.2 (12 at `xhigh`, 4 at `low`) |
| 4 | author the rest | no | 0 | none |
| 5 | calibration | **yes** | about 150 | $240 to $540 (100 at `xhigh`, 50 at `low`) |
| 6 | registration | **yes** | 0 | none |
| 7 | measured run | **yes** | about 256 | $435.2 to $1,011.2 (192 at `xhigh`, 64 at `low`) |
| 8 | analyze, rule on G4 | operator rules | 0 | none |

The 13 pilot runs are the proxy control (arm A, two runs on the open bridge network and two through the proxy in log-all mode) and 3 tasks times A, B, C times 1 run; the spec says "about 12". The 3 smoke runs (one per arm, so 2 at `xhigh` and 1 at `low`) are a separate model call and are not in that 13; the table counts them (16 runs: 12 at `xhigh`, 4 at `low`: 12 x $2 + 4 x $0.8 = $27.2, 12 x $5 + 4 x $0.8 = $63.2). The gate 7 figures are 192 x $2 + 64 x $0.8 and 192 x $5 + 64 x $0.8. Calibration is about 50 candidate tasks times (A twice + C once); the measured run is 32 tasks times (3 + 3 + 2).

### Gate 1 — mine

```
$S5 mine --repo codescout=/home/marius/work/claude/codescout --repo claude-plugins=/home/marius/work/claude/claude-plugins
```

Writes `tasks/candidates.json` (the structural rules of `mine.mjs`: subject starts with `fix`, one parent, authored strictly after `--since`, a test file and a source file changed, at least 2 source files or 40 source lines, nothing under `effort-steering/`, deduplicated by `git patch-id --stable`, at most 4 per subsystem). `mine` reads every ref (`--all`, the default of `mine.mjs`; the CLI has no flag for it) of each checkout through git. ### Gate 2 — pilot tasks

A Sonnet subagent drafts about 8 task definitions under `effort-steering/spikes/s5/tasks/<id>/` (`task.json`, `TASK.md`, `prompt.txt`, and `extra-tests/` when `task.json` lists `hidden.extra`); an Opus review checks each against the checklist below. Then, **one command at a time** (rule 12). Gate 2 runs under **draft limits**: pass the `cpus` and `memoryGb` you mean to register (`--cpus <n> --memory-gb <n>`, or `--prereg <work-root>/configs/<config>.json --mode <m>` once a config exists), because the gate's flaky filter and its build-timeout check are measured under them (R150). The pilot settles the limits (gate 3), and **every task is re-gated after that** with the final ones (`gate.json` is rewritten; it does not record the limits it ran under).

```
$S5 images                       # builds s5/codescout, s5/plugins, s5/proxy; prints the image ids (needs the network for base images and apt)
$S5 build effort-steering/spikes/s5/tasks/<id>
$S5 warm <id> --cpus <n> --memory-gb <n>   # cargo tasks: cargo fetch --locked in a container on the default bridge network (it has a route out; so does the proxy, and the pilot's --open-network runs), then a cold build with no network
$S5 gate <id> --cpus <n> --memory-gb <n>   # exit 0 only when ok; the reasons are printed, the detail is in <work-root>/tasks/<id>/gate.json
```

`build` prints the three hashes that go into the config; a built task is never overwritten (remove its directory on purpose first). A gate that is not ok means the task is dropped or rewritten, not that the gate is wrong (reasons: see the header of `gate-task.mjs`).

**Authoring rules** (what `task.json` must say; the loader checks what it can, the rest is the review's).

1. **List every file that holds a pass-to-pass name in `hidden.files`** (R151; `task-def.mjs` header). At grade time `graftScript` (`grade.mjs`) replaces the paths of `hidden.files` and `hidden.extra` in the agent's tree with the fix commit's version (and appends the `graftLines`), and touches no other file. For a test file the fix did not change, the fix commit's version is the one at P, so listing it restores it: an agent that weakened or deleted an assertion of an existing test to get green then loses that edit. A pass-to-pass name in a file that is not listed runs in the agent's own, possibly edited, version. This is anti-conservative for the non-inferiority claim (the spec: weak tests inflate scores), and a less deliberate arm may be more prone to it. **No code checks it** (a test name does not map to a file), and it has a **residual**: a file the agent must edit itself, such as a source file that holds both the fix and inline unit tests, cannot be listed (the graft would overwrite the agent's work with the fix), so its pass-to-pass names stay exposed. The review decides, per task, whether to list, to narrow the pass-to-pass names to listed files, or to accept the exposure and record it in the review notes (not in `TASK.md`: the agent reads that file).
2. **The hidden tests must compile at P** (gate reason `compile_at_parent`, `gate-task.mjs`). This is **stricter than the spec**, which asks for fail-to-pass tests that "name only symbols that exist at P or that `TASK.md` names" (spec, "Gates for each built task", 3): a hidden test that calls an API the fix adds does not compile at P, the gate is not ok, and the task is dropped even when `TASK.md` names that API. The task set is therefore biased against fixes that add an API, and that bias is the cost of the design (R154). Name the behaviour through symbols that exist at P, or put the test in `hidden.extra` written against them.
3. **No "ultrathink" in `prompt.txt`** (R147; `build-task.mjs`). For a prompt with that word the policy returns `deep` (an explicit override wins over every rule, `core/decide.mjs`) and the hook gives **no** steer (`core/steer.mjs`), so B would get no steer: its decision log says `steered: false` and every B run of the task would end as infra `arm_mismatch` (re-run, then exhausted, and the task dropped). `build` asks `decide()` with the rules of the hook copy and refuses a prompt that does not come out `shallow`. (Whether Claude Code itself reads the word as a thinking keyword, which would change the thinking of every arm, is not verified here.)

**Opus task review: checklist.** For each task, read `task.json`, `TASK.md`, `prompt.txt`, the tree at P and the fix, and answer yes to all of: (a) nothing in the tree, `TASK.md`, `prompt.txt` or the task id names the fix, its root cause, the issue slug or an identifier the fix introduces (the `scrub` terms are a floor, not the review); (b) `TASK.md` states the expected behaviour and constraints, not the fix; (c) every fail-to-pass test would pass for a correct fix with a different internal design (it names behaviour, not a name only this fix has); (d) the hidden tests compile at P (authoring rule 2) and fail by assertion; (e) **every file that holds a pass-to-pass name is listed in `hidden.files`**, or the task says why it cannot be (authoring rule 1); (f) the pass-to-pass names are the existing tests of the touched modules, scoped to run in minutes; (g) the fix does not change `Cargo.lock` (rule 7). A task that fails any item is rewritten or dropped.

### Gate 3 — pilot (operator approval)

Prepare two configs (any canonical JSON file outside `/tmp`; `proxyAllowlist` must be non-empty even in log-all mode, so put a placeholder such as `api.anthropic.com` in it for now): `pilot-control.json` with `arms.A.runs: 2`, `B.runs: 0`, `C.runs: 0` and one task; `pilot.json` with runs `1, 1, 1` and 3 tasks. Fill every field from the list in "What the registration holds". Rewrite each file canonical first (rule 2). Every run on the default network goes through the proxy, so the proxy must be up first (`runBatch` refuses a batch whose proxy container is not running, preflight item 5), and the batch also checks the id of the proxy image against the config's `images.proxy` (preflight item 3): that field must be the `s5/proxy` id of `$S5 images`.

Start the proxy in discovery mode, then the smoke (one rep-0 run per arm, on one task; this calls the model):

```
$S5 proxy up --log-all
$S5 run --mode smoke --prereg <work-root>/configs/pilot.json --tasks <id>
```

`smoke.ok` in the Summary must be true: the first user text equals `prompt.txt`, a decision log exists in every arm, B is steered while A and C are not (`bSteered`, from the decision log), **the steer reached the model** (`steerDelivered`, R147: counted in the transcript, the Row's `steerContexts` is 1 in B and 0 in A and C), and no run ended `infra_exhausted` (`run.mjs`, "SMOKE"). A smoke run whose checks fail still exits 0: read `smoke.ok`. `steerDelivered` rests on one assumption about the transcript, that the hook's context is written as an `attachment` record of type `hook_additional_context` for the event `UserPromptSubmit`, its `content` a list holding the sentence; the 42 real Claude Code 2.1.292 transcripts under `~/.claude*/projects` on this host that carry a `UserPromptSubmit` record of that type each carry exactly one, its `content` a one-element list holding the sentence (the other files that merely mention the sentence carry none), but a surprise shows here as `steer_mismatch` on every B run and a `steerDelivered` false, which is the point of the check. **Where to look first if it does:** open the transcript of one B run, `<work-root>/runs/<runId>-a<N>/config/projects/*/<sessionId>.jsonl` (the session id is the Row's `sessionId`), and grep it for `hook_additional_context`: a record of that type that holds the sentence but is shaped differently from the description above means the check must be adapted (`hookContexts` in `usage.mjs`); no such record at all in any B run means the steer really does not arrive. One B run in a long batch that ends `steer_mismatch` while the others are fine is the policy CLI missing its 500 ms limit (rule 10), not a shape problem. A shape problem is paid for: each B run is attempted `1 + infraRetries` times before it is exhausted, so stop the batch (Ctrl+C) as soon as the smoke shows it.

Proxy control. The input size of the **first request** must match exactly between the open-network runs and the proxied runs (the wire recorder doubled it once), and thinking and output must agree within the run-to-run spread:

```
$S5 run --mode pilot --prereg <work-root>/configs/pilot-control.json --tasks <id> --open-network --rows <work-root>/rows-pilot-open.jsonl
$S5 run --mode pilot --prereg <work-root>/configs/pilot-control.json --tasks <id> --rows <work-root>/rows-pilot-proxy.jsonl
$S5 proxy log                    # the hosts Claude Code needed: this is the allowlist
$S5 proxy down
# put those hosts into proxyAllowlist of pilot.json (and of the later configs), re-canonicalise the file (rule 2), then:
$S5 proxy up --prereg <work-root>/configs/pilot.json --mode pilot        # now with the allowlist from the config
$S5 run --mode pilot --prereg <work-root>/configs/pilot.json --keep-run-dirs
```

Two rows files are used for the control because a run id (`<task>.A.0`) is the same in both and a final row makes a run done; `--open-network` is accepted for `--mode pilot` only. The log-all proxy stays up from the first command to `proxy down`, so `proxy log` also shows the hosts of the smoke runs; it is the list of hosts, not a count of requests per arm. Measure and write down: the client cost estimate per run, the plan usage (the operator reads the usage page before and after), the run wall time (it sets the limit T: about 3 times the median A run, with a cap, per the spec), the grade time (`grade.wallMs`) and the disk per run (`du -s` on a kept run directory; `--keep-run-dirs` is what keeps `work/` and `target/`, which `runOne` removes after every run). Check the pilot items in rule 9.

After the pilot:

- **Fix `limits.cpus`, `limits.memoryGb` and `limits.timeoutMinutes`, then re-gate every task** with them (`$S5 gate <id> --prereg <config> --mode <m>`), because gate 2 ran under draft limits (R150). A task whose build now times out or whose tests turn flaky is dropped or rewritten.
- **`oom` per arm.** An out-of-memory kill inside the agent container is infrastructure whatever the run's outcome (spec), and the review's concern is that it may be arm-correlated (an `xhigh` agent may run more builds; not measured). Count the attempts that ended `oom` per arm; an exhausted line that ends in `oom` counts once (the line written without an attempt, `noAttempt`, is skipped):
  ```
  jq -rs 'map(select(has("type") | not) | select(.noAttempt != true) | select(.infra == "oom" or .lastInfra == "oom")) | group_by(.arm) | map("\(.[0].arm) \(length)") | .[]' <work-root>/rows-pilot.jsonl
  ```
  A difference between the arms is the input to the exclusion rule (rule 5: a task with a run lost to infrastructure leaves all arms).
- **The proxy log lists more than the API.** `proxy log` in log-all mode also shows hosts such as the update and telemetry ones. The binary 2.1.292 knows `DISABLE_AUTOUPDATER` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` (strings in the binary), but **this runner sets neither** (the container's variables are, at most, the six pinned in `run.test.mjs`: the config and state directories, the holdout rate, the proxy, the target directory of a cargo task and the token). Choose the allowlist **on purpose**: a host you leave out is refused for every arm, a variable you add would reach every arm, and an auto-update download inside each container costs time and disk.
- **Delete the kept run directories** (`<work-root>/runs/*/work`, `target`) once measured: `--keep-run-dirs` leaves the agent's tree, which can hold the token if the agent wrote it there (R116 case 1).

The same as gate 2 for the remaining candidates of gate 1's file, to about 50 in all; `build`, `warm`, `gate` each (one at a time).

### Gate 5 — calibration (operator approval)

The config has `A.runs: 2`, `B.runs: 0`, `C.runs: 1` and all candidate tasks (calibration has no B arm). Calibration rows are never reused for measurement (spec): they live in their own file.

```
$S5 proxy down                  # the pilot's proxy is still up; proxyUp refuses while a container s5-proxy exists
$S5 proxy up --prereg <work-root>/configs/calibrate.json --mode calibrate
tmux new -s s5-calibrate      # then, inside tmux:
$S5 run --mode calibrate --prereg <work-root>/configs/calibrate.json     # rows: <work-root>/rows-calibrate.jsonl
$S5 select --rows <work-root>/rows-calibrate.jsonl
```

`select` reads calibration rows only (a row of another mode is refused, R142) and applies the drop rule fixed in the spec: `not_measured` (no counted A run or no counted C run), `never_solved` (A passes 0 of its runs), `effort_idle` (A passes every run and C passes every run); the rest are kept. If fewer than 32 tasks are kept, the operator chooses: curate more tasks or accept a wider margin.

### Gate 6 — registration (operator approval)

Write `s5-prereg.json` (canonical form, rule 2) with the kept tasks, then run the simulation for the registered numbers and **attach its output to the commit message**:

```
$S5 simulate --method <bound.method> --resamples <bound.resamples> --seed <bound.seed> --n-tasks <number of tasks> --runs-a <A.runs> --runs-b <B.runs> --runs-c <C.runs> --margin <margin> --alpha <alpha>
```

`simulate` with no options uses the numbers the tests use: 32 tasks, A 3, B 3, C 2, task pass rates uniform on 0.3 to 0.95, 1,000 trials of 1,000 resamples, margin 0.15, alpha 0.05, seed 20261008, method `paired-t`; it prints `niRate` and `gateRate` for two scenarios: `deltaB = -0.15, deltaC = 0` (`niRate` is the false non-inferiority rate and `gateRate` the gate's false-positive rate) and `deltaB = 0, deltaC = -0.3` (`niRate` is the power of the non-inferiority claim and `gateRate` the gate's power). Register `bound.method` as `paired-t` (rule 1). **State the power at registration**: at a true delta of 0 the planned non-inferiority power is **0.722**, not the "about 75 to 85 percent" the spec plans for N = 32 (the second scenario's `niRate` in the default run above: 0.722; `deltaC` does not move it; the first scenario gives 0.048 and 0.053 for the false-positive rates, and the gate's power is 0.995). The simulation assumes pass rates uniform on 0.3 to 0.95, for which `E[p(1-p)]` is 0.199, the top of the range the spec sizes N from (0.15 to 0.20, which needs 27 to 37 tasks: 36.5 by the spec's formula at 0.199), so N = 32 gives less than the planned 75 to 85 percent; put the 0.722 and its assumption in the commit message beside the other numbers. Commit `s5-prereg.json` by explicit path; the measured run refuses it unless its bytes equal the HEAD blob.

### Gate 7 — measured run (operator approval)

```
$S5 proxy down                  # the calibration proxy is still up
$S5 proxy up --prereg effort-steering/spikes/s5/s5-prereg.json
tmux new -s s5-measure        # then, inside tmux:
$S5 run --mode measure --prereg effort-steering/spikes/s5/s5-prereg.json --stop-at-cost <usd>
```

`--stop-at-cost` overrides `stopAtCostUsd` of the registration for this invocation (the rows file is summed, so the stop survives a resume), and `--concurrency` overrides `limits.concurrency` the same way: **the Summary prints the `concurrency` and `stopAtCostUsd` the batch actually used** (R153), the rows record neither (only a `stopped` line carries the limit it stopped at), so keep the Summary of every invocation. The sum that the stop rule reads counts a run that timed out (no JSON, so no cost), was interrupted, or hit a plan limit (rule 19) as the **largest cost known in the file** (R148; no price table, so it is an estimate: `Summary.costEstimatedRows` says how many rows were estimated; the estimate is 0 until one cost is known). The token: **a stale exported `CLAUDE_CODE_OAUTH_TOKEN` wins over `~/.config/s5/token`** (it is value-checked, the file is not read), so unset it before a run that should use the file. `--tasks` is refused in measure mode (by `planRunsS5`; the CLI answers exit 1). Resume after a stop by running the same command again: `planRunsS5` is a function of the registration alone, and the rows file says what is done. Watch with `tail -f <work-root>/rows-measure.jsonl`.

### Gate 8 — analyze

```
$S5 analyze --prereg effort-steering/spikes/s5/s5-prereg.json --rows <work-root>/rows-measure.jsonl > report.json
```

The Report is printed as JSON, **with `excluded` in full** (every registered task that is dropped from all arms, with its reason: `infra_exhausted_in_<arms>` when a run of it ended `infra_exhausted` and was never recovered (R149), else `no_counted_run_in_<arms>`, including registered tasks with no rows). The secondaries are descriptive and now carry, per arm, the cost per resolved task also **with** each counted timeout at the largest known cost (`costEstimated`, `usdWithEstimate`, `perResolvedWithEstimate`, R148) and the token totals (`tokens`: `main` and `total` sums of `input_total`, `cache_creation`, `cache_read`, `output`, `thinking` over the counted rows of the included tasks, R153). `mechanism.thinking` keeps its own verdict (it is the registered test); `mechanism.output` and `mechanism.total` are printed as `signedDelta` and `pValue` only, never as a verdict (descriptive, R62). A note on stderr says how many typed lines and lines without a `runId` were skipped. **`analyze` refuses a rows file that holds a row whose `mode` is not `measure`, or that has none** (R142; exit 1, the message names the line and the mode), so pilot or smoke rows can never be counted as measured; `select` does the same for any row whose mode is not `calibrate`. A `type` line is not a row and is not checked. To use rows of another mode **on purpose** (say, to look at a pilot file with `analyze`), copy them into a NEW file with the mode changed, and give that file to the command; the CLI will not do it for you:

```
node -e "const fs=require('fs');for(const l of fs.readFileSync(process.argv[1],'utf8').split('\n'))if(l.trim()){const r=JSON.parse(l);if(!('type' in r))console.log(JSON.stringify({...r,mode:process.argv[2]}))}" <from-rows.jsonl> <new-mode> > <new-file.jsonl>
```

(it drops the `type` lines and rewrites `mode` on the rest; never write over `rows-measure.jsonl` with it). Write the result into ES-22; the operator rules on G4.

## 3. Instrument rules

Short, one per paragraph, each with its source. Where the code enforces a rule, it says so; the rest a person must do.

1. **Register `bound.method` as `paired-t`** (R76; `analyze.mjs` header, `analyze.sim.test.mjs` header). The brief's tie rule would take the percentile bootstrap, but the spec's own criterion (at a true delta of -0.15 non-inferiority is claimed in at most about 5 percent of trials) is met by `paired-t` and not by the percentile bootstrap, which is anti-conservative at N = 32. Over seeds 1 to 40 (40,000 trials per method, 1,000 resamples; re-run for this README on 2026-10-09 and the numbers reproduced): `paired-t` false non-inferiority rate mean 0.0482, max 0.066, 1 of 40 seeds above 0.065; percentile mean 0.0594, max 0.082, 5 of 40 above 0.065. The module default is `paired-t`; both stay selectable by the registration. For `paired-t`, `bound.resamples` may be 0 (it does not resample); the log-ratio intervals still use at least 2,000.
2. **Canonical JSON** (R65; `prereg.mjs`). Both loaders require the file's bytes to equal `JSON.stringify(parsed, null, 2) + '\n'`, so a repeated key or a value such as `0.10` cannot make a committed registration read two ways. The refusal names the file and the rewrite command (a repeated key collapses to its last value, which the commit then shows):
   ```
   node -e "const fs=require('fs'),f=process.argv[1];fs.writeFileSync(f,JSON.stringify(JSON.parse(fs.readFileSync(f,'utf8')),null,2)+'\n')" '<file>'
   ```
3. **A config is not a registration** (R2, R59). Only `loadS5Prereg` sets `registered: true`; the file may not carry a `registered` key; `runBatch` refuses `measure` without the marker.
4. **The prompt** (R98, R99, R111, R118; `build-task.mjs`, `run.mjs`). `prompt.txt` is stored beside `manifest.json` (never inside `tree/`) and sent to the CLI **byte for byte** as ONE argument after `--`. `build` refuses a prompt that is not UTF-8, that holds a NUL byte, or that holds an explicit "ultrathink" (R147, authoring rule 3), and a run refuses a `prompt.txt` whose sha256 is not the manifest's `promptHash`. The check that the transcript's first user message is the prompt (`firstUserTextOk`) compares after `trimEnd()` on both sides: a trailing newline is the one benign difference.
5. **The rows file** (R100, R133, R123; `run.mjs`). JSONL, append-only, one line per **attempt**. A Row has `runId` (`<taskId>.<arm>.<rep>`), `final` and `infra`: an infrastructure attempt that will be re-run has `final: false, infra: <reason>`; the last allowed attempt is written `final: true, infra: 'infra_exhausted'` (+ `lastInfra`); a counted row has `final: true, infra: null`. **A line with a `type` key is not a Row** (the `stopped` line: `{ type: 'stopped', at, reason, costUsd, limit, mode }` and, for `infra_streak`, `streak` and `lastInfra`, and, for `plan_limit`, `planLimit`), and `select`/`analyze` skip it and every line without a `runId`. Every line carries `mode`, and a batch refuses a rows file with a row of another mode: run ids are the same in every mode, so **each mode has its own file** (default `<work-root>/rows-<mode>.jsonl`); `analyze` and `select` refuse a row of the wrong mode too (R142). One batch at a time per work root (`batch.lock`, with the pid, mode and rows file; a lock whose pid is dead is replaced; after a hard kill the refusal names the file to delete if the pid number was reused). Only counted rows enter the analysis (`final` and `infra: null`); a timeout is a counted failure; an exhausted run is never counted. **A task is dropped from all arms, and shown in `excluded`, when a run of it ended `infra_exhausted` and was not recovered** (R149; `analyze.mjs`; spec: "dropped from all arms, never from one"): scoring it on the runs that survived would select runs, because exhaustion is not arm-neutral (the final review's reasoning, not measured: `arm_mismatch` and `no_log` arise only through the hook path, and `oom` covers an inner out-of-memory kill of the agent's own build). A run counts as recovered when a counted row has its `runId` (that is what `--retry-exhausted` produces, rule 13; the exhausted row stays in the file as evidence). A task with no counted run in an arm is dropped the same way. So an outage that exhausts runs shrinks the task set until the runs are recovered.
6. **Task commands** (R30, R53; `task-def.mjs`). `loadTaskDef` refuses a command that breaks these: in a cargo task every `f2p`/`p2p` command starts with `cargo` (no `env`, no `sh -c`) and a `cargo test` carries `--no-fail-fast` before any `--` (the gate cannot see a missing one: every test passes at the fix); in a node task it starts with `node` and runs `node --test --test-reporter=tap <file>`, both options **before** the first positional argument and in `--opt=value` form (on node v26.10.0 `node --test a.test.mjs --test-reporter=tap`, or a plain `node a.test.mjs`, prints spec output that the grader cannot read, and the gate drops the task). The `sh` runner is free.
7. **Fixes that change `Cargo.lock` are dropped** (R47). The grade has no network and the agent no route to the internet, so no agent fix can add a dependency; the gate reports such a task as `fails_at_fix` and `hidden_test_not_run`. The task set is biased away from dependency-adding fixes, and that bias is the cost of the design. This is a ruling, not code: `mine` does not pre-filter it.
8. **An early stop or check-in is judged by hand** (spec "failure modes"). The row keeps only `finalTextTail` (the last 300 characters of the agent's final text) and `testsRunBeforeDone`; read the failed runs' `finalTextTail` to tell a run that stopped to ask from one that finished wrong. Nothing in `analyze` decides it.
9. **What the pilot must confirm** (R88, R108, R139). (a) The stdout field names `total_cost_usd`, `num_turns` and `is_error` of the pinned CLI: if they differ, `costUsd` and `numTurns` are `null` in the rows until the names are fixed. (b) `exit.code` over the pilot's rows: whether 130, 137 or 143 ever occur in a normal run (without a timeout they are classified `interrupted`, infra; a 137 with `timedOut` true is the harness's own timeout kill and stays a final model failure, R90, R132). (c) `tokenScrubbed`: above 0 in any row means the CLI exposed the token to its tools (the files holding it were redacted in place). (d) Stdout that holds no JSON result with exit 0 (R139 b): no rule covers it yet; if the pilot shows one, add `exit 0 with no JSON result = infra no_result`. (e) Whether the CLI honours `HTTPS_PROXY`: the log-all control shows it. (f) The first-request input size (rule in gate 3).
10. **Watch `steer_mismatch`, `arm_mismatch` and `no_log`** (R89, R147; `run.mjs`, `effort-steering/adapter/claude-code/run-policy.mjs`). The hook gives the policy CLI 500 ms (`POLICY_TIMEOUT_MS`), kills it at the limit and fails open with no steer, and the CLI appends its decision-log record **before** it prints its result (`bin/effort-policy.mjs`): so a B run can have a log that says treated and steered and a transcript with no steer in it. `runOne` therefore checks both. The log (R89): B treated and steered, A and C held out; a missing log is infra `no_log`, a log that differs is `arm_mismatch`. The transcript (R147, step 6b, after the effort check): arm B must hold **exactly one** `UserPromptSubmit` hook context, equal to `phrases.shallow` of the hook copy's `core/steer.table.json` (read when the run starts); A and C none; anything else is infra `steer_mismatch`, and the Row's `steerContexts` is the count. All three are re-run and never scored. A rate of such rows in the smoke or the pilot is the sign (the final review's concern is that container CPU limits make a slow `node` start, and so the 500 ms window, more likely; not measured).
11. **Never mount `<work-root>/tasks/<id>/` read-write** (Task 8 carry; `prereg.mjs` `checkTasksMatch`). A run mounts reflink copies of the tree and the target (`work`, `target`); a grade mounts those copies and `hidden/` read-only; `checkTasksMatch` follows a symlink planted in that directory. The one rw mount under `tasks/<id>/` is `warmTask`'s `target/` (a sub-directory, created fresh).
12. **One thing at a time** (R122, R134 c, R123; `run.mjs`). At its start a batch removes every container that carries **both** labels `s5=1` and `s5.task`, whichever work root it belongs to; `warm`, `gate`, `grade` and the Docker-mode test suites (`S5_DOCKER_TESTS=1`) start containers with those labels too. So run **one** batch, gate, warm or Docker-mode suite at a time, and do not start `warm`, `gate` or `grade` while a batch runs. The proxy (`s5=1`, `s5.run=s5-proxy`, no `s5.task`) survives the sweep. About 20 unrelated containers run on this host: only `s5=1` containers are ever touched and nothing is pruned.
13. **`infra_streak`** (R124, R125). When `2 * (1 + limits.infraRetries)` infrastructure attempts follow each other, the batch stops with reason `infra_streak`. Look at Docker, the proxy (`docker ps --filter label=s5=1`) and the disk first, then resume with the same command, adding `--retry-exhausted` if runs were exhausted: a run whose latest final row is `infra_exhausted` is then planned again with a fresh allowance; the exhausted row stays in the file as evidence. An outage is recovered by that act, never by editing the rows file. `interrupted` rows are infrastructure and are re-run.
14. **Run batches under tmux** (R139 c, R141). A closed terminal is then a graceful stop through the SIGHUP handler; do not rely on `nohup`. The **first** Ctrl+C (SIGINT, SIGTERM or SIGHUP) is a graceful stop: nothing new starts and the runs in flight finish, which can take as long as the longest run needs (up to `limits.timeoutMinutes`; the ledger's figure is 90 minutes, plus the run's grade). The **second** signal ends the harness at once and leaves the clients and containers, which the next batch's sweep removes; the paid run in flight has no row. A `gate` or `warm` interrupted by Ctrl+C also leaves its container running (it carries `s5=1` and `s5.task`; the next batch sweeps it).
15. **`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is never set** (R108). It would switch off `--dangerously-skip-permissions` and need bubblewrap in the image: a different instrument. Neither this CLI nor `runOne` sets it (nor `GITHUB_ACTIONS`); a value in the operator's environment does not reach the container (the container's variable list is pinned by a test in `run.test.mjs`). To keep the token out of the transcripts anyway, `runOne` redacts it in `config/` and `state/` after every run (`tokenScrubbed` counts the files that held it).
16. **The usage rule** (finding of 2026-10-07; `usage.mjs`). Per `message.id` the record with the **largest** `usage.output_tokens` counts (the last on a tie), never the first: early records of a message carried partial usage in 13 of 596 multi-record messages in this session's tool-loop transcripts. The main transcript and every `subagents/**/agent-*.jsonl` count; an id already counted is not counted twice (a forked subagent repeats its parent's ids).
17. **`grade <runId>` needs a kept run directory.** `runOne` removes `work/` and `target/` after every run, so only a run started with `--keep-run-dirs` can be re-graded; the CLI takes the highest attempt number that still has a `work` directory, prints the grade and writes no rows. The kept `work/` can hold the token if the agent wrote it there (R116 case 1). The re-grade uses the image tag of the task's repo (not the id the run was pinned to) and, with `--prereg` or `--cpus` / `--memory-gb` (R150), the CPU and memory limits of the registration; without them it passes none, an unconstrained container. It starts a container labelled `s5.task`: rule 12 applies.
18. **The agent can see the steering code** (R154, S4 carry-over; `run.mjs` mounts). The hook copy is mounted read-only at `/opt/es` in every arm, so the agent can read the rules, the table and the adapter; `/run/config` and `/run/state` are mounted read-write, so it can also write the transcript and decision-log directories it runs in. This is equal across the arms. The spec excluded `effort-steering/` tasks for awareness reasons ("a task about the steering code could make the agent aware of the steer"); `mine` does, and the mount is the part of the box that stays visible.
19. **`plan_limit`** (R-PL3 to R-PL5, R-PL9; `../plan-limit.mjs`, `run.mjs`, `cost.mjs`). When the Claude plan is spent, the CLI prints a refusal such as `You've hit your limit · resets 3pm` and may return it as the ordinary response; graded, it would be a model failure invented for the arms that burn the most plan usage (`xhigh`). `runOne` therefore looks for one (step 2c) in the stdout envelope's typed `api_error` and `result`, in stdout, and in the last assistant record of the main transcript, for every run that got that far, **a container that timed out included**, and **before** any step that reads the transcript: a refusal is never reported as `api_error`, `no_transcript` or `transcript_unreadable` (the real 401 authentication failure stays `api_error`). A hit is infra `plan_limit`: `final: false`, never graded, and the Row carries `planLimit: { source, matched, resetHint, rateLimitType, resetsAt }` (`matched` at most 200 characters, the token redacted before the cut). The batch does not retry it and **stops**, with the line `{ type: 'stopped', at, reason: 'plan_limit', planLimit, costUsd, limit, mode }` (`limit` is the cost limit, as for `hidden_changed`; `Summary.stopped` carries the same). **What to do:** read `planLimit.resetHint` (for example `resets 3pm`) on the stopped line, wait for the reset (or add credits), and **run the same command again**; the refused run is planned again like any run with no final row. A `plan_limit` row says nothing about the run, so it does **not** use one of the run's attempts (three plan windows in a row do not write `infra_exhausted`, which would drop the task from all arms, rule 5), it is **not** a step of the `infra_streak` count (it neither adds to it nor resets it, on a resume too), it is never the row an exhausted line is copied from, and `analyze` ignores it in its primary analysis like any non-final row (no counted row, no exclusion), but `secondaries.counts[arm].infraRows` DOES count it, as an infrastructure attempt of the arm whose run was in flight when the plan ran out (`infraRows` counts every row with an infra value except a `noAttempt` line), so read that figure with the stopped lines beside it. In the stop rule a `plan_limit` row with no cost is estimated like an interrupted one, as the largest cost known in the file (R-PL9; `Summary.costEstimatedRows` counts it), because a refusal can come part-way through a run and print no JSON.

   **The detector fails closed, on purpose, and a recurring false stop blocks the batch.** It mirrors the CLI's own classifier of usage-limit messages, which is as wide as a `startsWith`: a text that begins (at index 0, at most 600 characters) with `You've hit your`, `You've reached your`, `Opus requires usage credits.` and the like is a hit even when it is prose the agent wrote, for example `You've hit your target of 90%…`, `You've reached your goal…` or `Opus requires usage credits. I switched…`. A false miss would grade a refusal as a model failure and silently corrupt the study, so the detector prefers the false stop. That stop is **not** cheap when it repeats: a `plan_limit` row uses none of the run's attempts and the run is never exhausted, so the refused run is planned first again on every resume, each resume pays one full agent run, and with `concurrency` 1 the batch makes no progress at all while the trigger lasts. **How to diagnose it:** read `planLimit.source` and `planLimit.matched` on the stopped line (or the row). `transcript_note` comes from a task prompt or a hook text that starts with a marker (`[Usage limit reached`, `[Usage limit approaching`), or from a record carrying `usageLimitNote`: that is deterministic, it will recur on every resume, so fix that task prompt or hook text. `stdout`, `envelope_result` or `transcript` with prose is the model's own opening words: that is sampled and rarely repeats, so resume. `matched` naming a real refusal with a `resetHint` is the plan: wait and resume. **Today there is no operator override**: no flag accepts a run past a false stop, and no cap on repeated stops. The study's own prompts and steer phrases were checked and do not start with a marker: the seven pilot `prompt.txt` files under `tasks/` (no line starts with `[Usage limit` or `You've hit/reached your`), and `phrases.shallow` and `phrases.deep` of `core/steer.table.json`. The detector also reads the CLI's wrap-up note anywhere in the main transcript, the task prompt and the hook context included (a record with `usageLimitNote` `wrap_up`, `near_limit` or `release`, or a text that starts `[Usage limit reached` or `[Usage limit approaching`): the CLI then told the model to finish or checkpoint because the plan was spent or nearly so, and the run is not gradeable.

## 4. Not verified

- **The Docker paths of this CLI have not been run.** The tests inject every module; `images`, `proxy`, `warm`, `gate`, `run` and `grade` have not been run against a Docker daemon through this CLI by the author of this file. The modules they call have their own tests, some of which need `S5_DOCKER_TESTS=1`.
- **The cost figures** in the table are my multiplication of the spec's published per-run figures, not a measurement. The pilot is where they get replaced.
- **The 90-minute figure** for a graceful stop comes from the ledger and the example registration; the real bound is the registered `limits.timeoutMinutes` and the grade time.
- **R139 b** (`claude -p` cut off by SIGINT probably exits 0 on 2.1.292) is a static reading recorded in the ledger; no model call was spent on it.
- **Whether `claude` 2.1.292 honours `HTTPS_PROXY`** and which hosts it needs: only the pilot's log-all control can say.
- **A policy CLI killed after it wrote its decision log but before the steer reached the hook** (the CLI appends the record before it prints its result: `bin/effort-policy.mjs`) shows a correct decision in the log. That window is read from the code, not observed, and since R147 the transcript check (`steer_mismatch`, rule 10) is what catches it. - The CLI exits `0` for a batch that stopped by a rule or for a smoke run whose checks failed: the exit code does not say how the batch went; read `stopped` and `smoke.ok` in the Summary (R144).
- **The real plan-limit envelope and transcript have not been observed** (rule 19). No instance of a plan-limit hit exists on this host: `../plan-limit.mjs` was built from the CLI binary's message list (the CLI's own classifier of usage-limit messages, read in 2.1.292 and 2.1.296), the typed fields of its SDK schema, and the shape of a real authentication-failure (401) envelope and transcript record, and every test that builds a refusal says it is synthetic. Not verified: that `--output-format json` puts `api_error` or `api_error_params` on the result envelope (the typed channel is an optional extra, never required); that the transcript file persists `apiError`, `apiErrorParams` or `usageLimitNote` on a record, and where the CLI delivers the wrap-up note; that a refusal reaches stdout (or the last assistant record) of a `-p` run in the form the patterns expect. `runOne` reads the stdout envelope, stdout and the main transcript (the last assistant record, and the wrap-up note anywhere in it); it does **not** read the container's stderr, which the detector would accept (a test pins this: a refusal only on stderr is graded). The first plan-limit stop in a real batch is the first test of all of this: read `planLimit.source` and `planLimit.matched` on its stopped line.
- **A refusal that no pattern matches and that carries no typed `apiError` is not detected** (rule 19): a prefix such as `Error: ` or `API Error: `, ANSI colour, a text over 600 characters, or a text outside the CLI's own classifier (the CLI sets `apiError` only when its classifier matches). If the record is an API-error record it shows up as `api_error` attempts, then `infra_exhausted`, then `infra_streak`, loud but misattributed; if the CLI returns the refusal as an ordinary `is_error: false` response it is graded as a model failure, silently.
- **Not built (plan_limit follow-ups, rule 19):** an explicit operator act to accept a run past a false stop (for example an accept flag naming a runId), a cap or different handling for a run that stops repeatedly with a non-typed hit, and a preflight check of the task prompts and the hook text for marker-shaped starts. Today a recurring false stop is diagnosed by hand and fixed at its source.
